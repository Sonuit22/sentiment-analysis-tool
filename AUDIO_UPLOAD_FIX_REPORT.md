# Audio Upload Fix Report

## Root cause

Audio prediction used this request path:

    Browser -> Next.js /api/predict/audio -> FastAPI /predict/audio

The WAV multipart body therefore passed through a Vercel serverless function. Vercel rejected larger request bodies with HTTP 413 before the request reached FastAPI. Text prediction worked because its JSON payload is small.

## Files modified

- `frontend/lib/api.ts`
- `frontend/.env.example`
- `backend/app.py`
- `package-lock.json` (regenerated by the clean npm installation)
- `AUDIO_UPLOAD_FIX_REPORT.md`

No UI, loading state, model logic, transcription logic, or text-prediction flow was changed.

## Fix

`predictAudio()` now sends its browser-generated `FormData` directly to:

    https://sentiment-analysis-tool-a8nd.onrender.com/predict/audio

The public backend URL can be configured at frontend build time with:

    NEXT_PUBLIC_BACKEND_API_URL=https://sentiment-analysis-tool-a8nd.onrender.com

The deployed Render URL remains the safe default when that variable is absent.

The code does not manually set `Content-Type`. The browser supplies the required `multipart/form-data` header and boundary, preserving the upload correctly.

Text prediction remains unchanged:

    Browser -> Next.js /api/predict -> FastAPI /predict

## Error handling

The existing prediction component still owns loading, success, and error state. It disables the Analyze button while awaiting the request and restores it in `finally`.

Response parsing now reads the response body once, parses JSON when possible, and preserves plain-text bodies otherwise. FastAPI `detail` messages such as `Upload a WAV audio file.`, `Speech could not be understood.`, and `Speech recognition is unavailable.` are surfaced through the existing UI error component instead of being replaced by a generic HTTP-code message.

## CORS

The FastAPI backend permits POST requests with arbitrary request headers and now always includes Vercel application origins in its CORS regex. A custom `ALLOWED_ORIGIN_REGEX` is additive and can no longer accidentally replace Vercel support. The exact production Vercel origin may also be included in `ALLOWED_ORIGINS` on Render.

The live Render service returned HTTP 400 during the preflight test performed before this backend change was redeployed. Render must be redeployed before browsers can use the direct upload. After redeployment, the same Vercel-origin preflight is expected to return HTTP 200; the source-level CORS test verifies that policy.

## Final request flow

    Text:  Browser -> Vercel proxy -> Render /predict
    Audio: Browser ----------------> Render /predict/audio

Bypassing Vercel removes its serverless request-body limit from audio uploads. Any remaining size limit would be imposed by the browser or Render rather than the Next.js proxy.

## Verification

- A clean npm installation restored the complete Next.js dependency tree.
- The Next.js 15 production build passed compilation, linting, TypeScript validation, static generation, and route tracing.
- Source inspection confirms text prediction still posts to `/api/predict`.
- Source inspection confirms audio prediction posts directly to the Render `/predict/audio` endpoint.
- A direct multipart silent-WAV request reached deployed Render and returned FastAPI's expected HTTP 422 JSON message: `Speech could not be understood.`
- A direct multipart non-WAV request reached deployed Render and returned FastAPI's HTTP 422 JSON message: `Upload a WAV audio file.`
- The currently deployed Render service returned HTTP 400 for a Vercel-origin CORS preflight, confirming the backend CORS source change must be redeployed.
- The updated FastAPI source returned HTTP 200 for the same Vercel-origin preflight, including the requested origin and allowed `GET, POST` methods.

## Deployment requirement

Redeploy both services:

1. Redeploy Render so the additive Vercel CORS rule becomes active.
2. Redeploy Vercel so the browser bundle uses the direct audio URL.

Set `NEXT_PUBLIC_BACKEND_API_URL` in Vercel's Production environment to the Render base URL. The built-in default uses the same URL, but the explicit variable makes the deployment contract visible.
